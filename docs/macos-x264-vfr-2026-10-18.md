# Apple M1 x264 presentation timing — October 18, 2026 UTC

The Mac x264 candidate budgets bits using actual presentation time when encoding falls below the requested frame rate. In this repeat, **both x264 and Apple VideoToolbox passed three packaged 720p60 → 4K60 → 720p60 workflows**, with no unreadable frame identities or disagreements between sampled rows. The earlier x264 picture failure remains documented in the [NV12 report](macos-nv12-conversion-2026-10-18.md). The new results support this targeted fix; they do not establish general picture quality, 4K60 capability or production readiness.

## Implementation and tradeoff

x264 previously used a fixed-rate budget even when the app delivered fewer input frames under load. The Mac backend now supplies the scheduled presentation clock to pinned x264 in variable-frame-rate mode. Capture timestamps and opaque source identities remain separate, so a static capture or caller identity cannot distort rate control.

This configuration retains **one input frame** before returning output. The app treats accepted input awaiting output as progress, and only increments sent-frame/byte counters for actual packets. Every returned packet retains its original input identity and capture timestamp. Invalid inputs do not consume the pending frame; unexpected delay/reordering abandons the encoder generation. Reinitialization discards the tail, and a long idle gap starts a fresh generation with a keyframe. The idle threshold is the larger of one second and three nominal frames, preserving ordinary 1–2 fps cadence. Keyframe requests are consumed on their input rather than retried because the preceding packet was a delta.

The extra buffered frame is a latency tradeoff: approximately one input interval in steady operation, longer at low frame rates. These workflows do not establish a complete capture-to-display latency or A/V-sync budget. Apple VT settings remain unchanged. Windows continues to use its original encoder call; the additional presentation argument and pending result are used by the Mac backend. **No VDO.Ninja API or signaling command was added.**

## Controlled native picture experiment

This supporting experiment supplies identical 420-frame deterministic inputs to the app's pinned x264, on a 60 → 20 → 60 fps presentation timeline. It uses the same 4 Mbps ABR/maximum, half-second VBV and veryfast/zerolatency baseline configuration. It is **not application testing**, an OBS comparison, or replay of the live browser's exact pixels.

| Timing configuration | Slow-phase payload, Mbps | Aggregate luma PSNR, dB | Mean luma SSIM | Independently decoded wrong identities, all 420 frames |
| --- | ---: | ---: | ---: | ---: |
| cfr60 | 1.346 | 20.82 | 0.7516 | 2 |
| vfr60 | 3.034 | 35.71 | 0.9720 | 0 |
| cfr20 | 3.875 | 50.36 | 0.9977 | 0 |

PSNR/SSIM are **x264-reported reconstruction metrics**, not external FFmpeg/VMAF scores. Aggregate PSNR is computed from frame MSE; SSIM is averaged over frames. FFmpeg independently decodes 420/420 frames for each configuration and compares the known identity of every input. The CFR60 control has two unanimously wrong identities despite zero unreadable/disagreeing rows. This exposes a limitation of identity readability alone. VFR has zero wrong identities here and retains one input frame.

CFR20 is an explanatory control, not the proposed app policy: using a fixed 20 fps budget also produces roughly 11–12 Mbps during the 60 fps phases. VFR recovery averages about 4.68 Mbps in this short experiment, so a configured 4 Mbps rate is not an instantaneous wire-rate guarantee. The aggregate native analysis is marked failed because its CFR control has two identity mismatches; the VFR case passes.
