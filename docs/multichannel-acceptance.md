# Multichannel audio acceptance

The requested outcomes are six independently preserved input channels, transmission to compatible receivers with a usable stereo fallback, and more than six independently editable recording tracks. Six channels inside one stream and six recording tracks are different things. A stereo device cannot demonstrate physical six-channel capture.

This is the working acceptance record. The feature is not complete while a required journey is unimplemented or untested. Build, lint, syntax and unit checks are gates only. Application results must identify the exact packaged executable/module hashes and retain the actual decoded output or measurements.

Status reconciled on 2026-11-14: the previous OBS row was stale. Native six-channel reception shipped separately in [ninja-plugin v1.1.80 on October 31](https://github.com/steveseguin/ninja-obs-plugin/releases/tag/v1.1.80). Its [validation record](../../ninja-plugin/docs/six-channel-validation.json) covers 12 actual OBS recordings across six local/packaged workflows, including source recreation, stereo downmix, and ordinary mono/stereo reception. Six-channel capture-boundary audio was synthetic. This does not qualify physical input hardware or turn the Game Capture candidate into a released sender.

Fresh packaged application rerun on 2026-11-14 passed four recordings: two in an OBS 5.1 profile and two in a stereo profile, each before and after source recreation. Both applications exited cleanly, and the loaded OBS module path was verified. The 5.1 recordings retained all six tone identities, with the largest unwanted tone approximately 61 dB below the intended tone. Evidence: [5.1 results](../../ninja-plugin/artifacts/six-channel-recheck-20261114/surround/results.json) and [stereo results](../../ninja-plugin/artifacts/six-channel-recheck-20261114/stereo/results.json).

Those runs used Game Capture candidate SHA-256 `cbd6d1dc334ca7bfbb44263fa0eced5937e6a9f0872926c2375e6b42ea320dff`, released plugin v1.1.80 SHA-256 `5e22112e55cff873eb4ce5eccce2494bd8623d799aeb01431ac230b61bbe9f51`, and portable OBS 32.2.2. Source audio was synthetic at the capture boundary; the rest of the encode/transport/decode/record path was real.

The OBS path is a 5.1 surround layout. Slot 4 is treated as LFE and is omitted from OBS's stereo downmix. Additional November 14 checks using 1300/1700/2300/2900/3100/3700 Hz confirmed that AAC recording loses the channel-4 voice-range tone. FLAC recording retained all six tones before and after source recreation. FLAC does not change the stereo downmix. Physical microphones, per-channel routing, full-band frequency response and editor import still need their own acceptance results.

## Output checks

Use a distinct frequency and a timed marker for each source/channel. Check decoded channel/track counts, ordering, cross-channel leakage, mute intervals, timestamp continuity and duration. Listen to the outputs as an additional check. Record file/stream names and codec/channel metadata. Verify failure behavior as well as the successful path: unsupported negotiation, source disappearance, receiver reconnect, and stopping during activity.

Preserve a distinction between real device/application workflows, synthetic input-boundary checks through packaged applications, and code gates. A passing result in one category does not stand in for another. Hardware/editor checks remain open until run on those actual targets.
